## 一、项目概述

### 1.1 背景

高校教师在建设课程时，需要将散落在教材、讲义、PPT 中的知识点整理成结构化的知识图谱，并据此为学生规划学习路径。人工建图成本高、维护难；学生缺乏"学到哪一步、下一步该学什么"的导航。

### 1.2 产品定位

面向教师与学生双角色的 **AIGC 驱动课程知识图谱构建与学习导航平台**：教师上传课程资料，系统自动抽取知识点与关系生成可交互图谱；学生浏览图谱、标记掌握状态、获得可解释的个性化学习路径，并可基于教材原文进行智能问答。

### 1.3 建设目标（可量化）

| 编号 | 目标 | 量化指标 |
| --- | --- | --- |
| G-1 | 降低教师建图成本 | 单份教材从上传到成图 ≤60 秒 |
| G-2 | 保证图谱教学可用性 | 知识抽取准确率 ≥70%，关系类型 ≥3 类，知识点 ≥20 个 |
| G-3 | 提供可解释的学习导航 | 推荐结果附带先修依据，非黑盒 |
| G-4 | 问答可信不编造 | 回答附参考章节；教材外问题正确拒答 |
| G-5 | 零门槛可运行 | 普通电脑可部署，无 GPU 依赖，无 Key 可演示 |

## 二、干系人与用户分析

### 2.1 干系人识别

| 干系人 | 角色 | 关注点 | 影响力 |
| --- | --- | --- | --- |
| 命题企业（杭州金扬智能） | 需求方 / 评审方 | 指标达成度、方案可落地性 | 高 |
| 高校教师 | 主要使用者（内容生产） | 建图效率、结果可修正性 | 高 |
| 学生 | 主要使用者（内容消费） | 学习路径是否清晰可信 | 高 |
| 课程教研组 | 间接使用者 | 多课程复用、资料版权合规 | 中 |
| 部署运维人员 | 支撑角色 | 安装复杂度、依赖多少 | 中 |
| 竞赛评委 | 评审方 | 演示效果、文档完整性 | 高 |

### 2.2 用户画像与诉求

**教师（teacher）**

- 特征：熟悉课程内容，不熟悉图数据库与提示词工程；时间紧。
- 核心诉求：上传即成图；抽错了能手动改；改完立即看到效果。
- 使用频次：建课时集中使用，学期中偶尔修订。

**学生（student）**

- 特征：自主学习能力参差，需要"下一步做什么"的明确指引。
- 核心诉求：图谱看得懂；问问题能得到教材内的答案；学习路径有理由。
- 使用频次：高频、碎片化。

**评委 / 演示场景**

- 核心诉求：现场无网络或无 API Key 也能跑通全流程。
- 该诉求直接催生了 **离线演示模式** 这一隐性需求（见 FR-11）。

## 七、关键用例

### UC-01 教师上传教材并生成图谱

- **参与者**：教师
- **前置条件**：已以教师身份登录
- **主流程**：
  1. 教师进入上传页，填写课程标识与课程名称；
  2. 选择 PDF 或 TXT 文件并提交；
  3. 系统校验文件类型与魔数，解析文本，按章节切块；
  4. 系统调用大模型抽取知识点与关系，合并去重后写入图存储；
  5. 系统返回知识点数、关系数与耗时分解；
  6. 教师进入图谱页查看结果。
- **扩展流**：
  - 4a. 未配置 API Key → 返回内置演示数据集，流程不中断；
  - 4b. 单个文本块抽取失败 → 跳过该块，其余继续，不中断整体；
  - 2a. 文件为改名的二进制 → 返回 400 拒绝。
- **后置条件**：课程与图谱持久化，学生端可见。
- **验收标准**：耗时 ≤60 秒；知识点 ≥20；抽取结果可人工修正。

### UC-02 学生获取学习路径

- **参与者**：学生
- **主流程**：
  1. 学生进入学习路径页；
  2. 勾选已掌握的知识点；
  3. 系统基于 PREREQUISITE 关系遍历，仅推荐先修已全部掌握的知识点；
  4. 按解锁价值、难度、章节顺序三重排序，每条附推荐理由；
  5. 学生再次勾选，推荐列表实时刷新。
- **验收标准**：不推荐先修未满足的知识点；理由可解释；勾选后即时更新。

### UC-03 智能问答与拒答

- **参与者**：学生
- **主流程**：
  1. 学生输入问题；
  2. 系统检索相关教材文本块；
  3. 系统将检索上下文交由大模型生成回答，流式返回；
  4. 回答附带参考章节标注。
- **扩展流**：
  - 2a. 教材内无相关内容 → 明确回答"教材中未涉及"，不编造。
- **验收标准**：单次响应 ≤15 秒；引用可溯源；教材外问题正确拒答。

### UC-04 教师自助接入自定义模型

- **参与者**：教师
- **主流程**：
  1. 教师进入模型接入设置页；
  2. 选择协议格式，填写接口地址与密钥，点击"一键测连通"；
  3. 系统发送最小请求验证可用性并返回时延；
  4. 教师点击"获取模型"载入可用模型列表并选择；
  5. 保存后配置立即生效。
- **扩展流**：
  - 4a. 端点不支持模型列表 → 提示手动填写模型名；
  - 2a. 地址指向内网或非 https → 拒绝保存（SSRF 防护）。
- **验收标准**：密钥不回显明文；配置生效无需重启；非法地址被拦截。

## 九、缺陷与需求澄清记录

> 本节记录实测中暴露的、需求阶段未能预见的问题。**保留此节的意义在于说明需求验证手段是否有效**，而非掩饰问题。

### D-01 在线模式知识抽取返回空结果（严重）

- **发现方式**：接入真实 DeepSeek Key 实测（离线演示模式无法发现）。
- **现象**：上传教材后抽取到 0 个知识点。
- **根因**：结构化输出在 `json_object` 模式下，DeepSeek 不会自动接收 schema 信封，返回裸数组，与期望的顶层对象结构不符。
- **需求澄清**：原需求 FR-03 只写了"抽取知识点"，未约定"模型返回结构契约"。已在提示词中显式声明顶层对象结构，并将"协议兼容性"纳入 FR-14 验收标准。
- **教训**：**离线演示通过不等于在线可用**，指标类需求必须以真实服务验证。

### D-02 图谱图例渲染为原始标记文本（一般）

- **现象**：图例位置显示 `<span style="color:#e5484d">— 前置</span>` 字面文本。
- **根因**：将 HTML 字符串传入图表库的纯文本绘制接口。
- **需求澄清**：FR-07 原验收标准只要求"含图例说明"，未规定实现方式。已改为真实 DOM 图例，同时改善可访问性。

### D-03 关系类型判定偏向泛化（已知残留）

- **现象**：CONTAINS 关系存在过度泛化，是关系准确率的主要失分点。
- **处理**：已纳入改进方向（两阶段关系抽取），当前由教师端手动修正兜底（FR-10）。
- **状态**：不阻塞验收，准确率仍达标（84.6% > 70%）。
